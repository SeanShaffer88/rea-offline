# Architecture

Implements the *Universal Offline Windows Client & REA Analysis Engine*
blueprint. Pure Rust, **zero external dependencies** — a clean checkout
builds on an air-gapped machine with nothing but a Rust toolchain.

```
User / CLI
 ├─ Mode A: scan ───────────────────────────────► REA Bridge ──► JSON report
 └─ Mode B: sandbox
      1. prepare %TEMP%\rea_sandbox_<id>\  (install\ work\ tmp\)
      2. registry hive mount (sandbox_reg.dat, best-effort, warned)
      3. baseline SHA-256 snapshot of install\
      4. installer in Job Object (suspended → assign → resume),
         stdout/stderr captured to work\installer.*.log (tails in report)
      5. post-install snapshot → delta (added / modified / deleted),
         plus a whole-sandbox delta catching drops into the redirected
         profile (only our own bookkeeping is filtered out: the hive file
         and the two work/installer.*.log capture logs — tmp/ is the
         installer's own temp folder and work/ its working directory, so
         what it leaves in either is a drop and is analyzed as one)
      6. REA analysis of install\  (external REA if found, else native)
         + native analysis of the installer binary (installer_report)
         + native analysis of the changed files outside install\
           (drops_report); verdict = worst of the three parts
      7. unmount hive → purge sandbox → verify zero residue
```

## Security model & honest limits

A Job Object is *containment*, not a hypervisor: it bounds lifetime
(whole tree dies with the job), memory, and (with the timeout) wall
clock, and the child gets a throwaway directory plus a redirected
per-user environment. It does **not** stop a determined installer from
writing elsewhere on disk or to the real registry if it runs elevated —
no user-mode-only design on Windows Home can. Run untrusted installers
from a standard (non-admin) account, and treat the delta + REA report
as the inspection record. Registry hive mounting additionally needs
`SeRestorePrivilege` (typically admin) and a valid hive file; when
unavailable the run continues with environment redirection and the
report carries a `registry_warning` field rather than failing silently.

That advice is only as good as the operator following it, so the run checks
it instead of assuming it. `src/containment.rs` records two facts a file
delta can never show: whether the sandbox process was **elevated** (Windows)
or **root** (POSIX) — in which case the installer could write outside the
tree no snapshot looks at — and whether the registry hive actually mounted.
Both live in the envelope's `containment` block, both are folded into
`coverage` when they mean evidence escaped, and `doctor` reports the session's
privilege level before a run is trusted. An elevation the platform will not
disclose is recorded as unknown rather than silently treated as "no".

The method's permanent blind spots — registry writes need a driver to
redirect, writes outside the sandbox tree are invisible to a Job Object,
there is no process/network/syscall telemetry, and a file created and
deleted between the two snapshots leaves no trace in either — are listed
once per report as `containment.limits`. They are deliberately *not* coverage issues: a warning
that is true of every run is a warning nobody reads, and it would make
`--fail-on-incomplete` useless. They are stated so an archived verdict can be
read months later without the manual.

## Coverage is a summary of the envelope, not a bystander

A report can state in one field that it never analyzed the installer while
claiming in another that it saw everything. `src/coverage.rs` exists to make
that impossible: the `coverage` block is *derived* from the envelope it
describes. Snapshot and analysis limits are added as they are encountered;
how the run ended (`universal_sandbox::run_issue`), what the sandbox could not
contain (`containment::issues`) and what the envelope records about itself
(`coverage::recorded_failures`) are folded in afterwards — each through the
same function the archive validator calls, so a writer and a validator cannot
disagree about what "complete" means. Recording is idempotent, so the block
stays a summary rather than becoming an append-only log.

Consequences worth knowing: an installer that could not be analyzed, or a
sandbox that could not be purged, makes a run incomplete — they are missing
evidence and a broken promise respectively, and both are failures the report
already admits in prose.

The same record covers the manual workflow. `snapshot` and `diff` are how a
machine where the sandbox cannot run is still inspected: snapshot, install for
real, diff. A delta inherits the blind spots of **both** manifests — two
snapshots that each failed to list the same directory agree completely, and
that agreement is not evidence — so `mode_diff` carries forward both sets of
issues, and both commands accept `--fail-on-incomplete`. Because those
documents are not validated on load the way an archived report is, the gate
derives incompleteness from the issues list rather than from the `complete`
flag: a record claiming completeness while listing blind spots is refused.

Inheriting blindness is only half of it: a delta also has to be *between two
things that can be compared*. `Snapshot::load` therefore refuses a document
that is not a manifest at all — no `root`, or no `entries` — rather than
letting a report archive load as "a snapshot of nothing" and diff into a
confident "everything was deleted". The entries get the same treatment: an
entry with no path, a duplicated path, or a size or hash of the wrong shape
is refused at load instead of being dropped, overwritten or defaulted,
because a manifest that loses entries on the way in is the same failure one
level down — a delta that claims complete coverage of evidence it never
held. The `issues` block gets it too: present, it must be a list of
string-fielded issue objects, since it is the record of what the snapshot
could not see and reading it loosely would erase the blindness it records;
absent, it stays allowed, because pre-coverage manifests have none.
Analysis is bracketed the same way capture is: a scan file whose size or
modification time moves between the reads its row is built from is refused
with a named issue rather than mixing versions. A missing `sha256` is the one deliberate exception: it loads as an
empty digest and diffs as `unverified`, which is exactly what an unreadable
file already means. `Snapshot::compare_issues` then states
what makes two otherwise-valid manifests incomparable: a different root, or
an `after` that predates its `before`. Both are coverage issues, not errors,
because a manifest stores root-relative paths precisely so it stays
comparable after the tree moves — the gate decides, the document reports, and
neither assumes.

## Offline REA

Set `REA_PATH` or pass `--rea C:\path\to\rea` (executable or Node `.js`
entry). If REA is absent, the native analyzer still produces hashes,
formats, PE metadata, indicators and a 0–100 risk score. External output is
captured through temporary files created with `create_new` (no symlink follow),
bounded to 32 MiB stdout / 1 MiB stderr, and removed on success, failure and
timeout. This avoids the classic pipe-buffer deadlock when REA emits a large
JSON report while stderr is also noisy.

## Coverage is not risk

Native directory analysis records operational limitations in
`report.scan_issues`: unreadable directories/files, external REA failures, and
files above the 32 MiB content-analysis limit (full-file hashes are still
computed). `summary.complete` is false when any issue exists. These fields are
additive within schema 3 and are shown by text, Markdown, and the GUI. They do
not add risk points: an access-denied error is not evidence of malice. Symlinks
are never followed by static directory analysis.

`report <archive.json>` validates saved evidence and renders/gates it without
revisiting the target. Schema 2 remains readable; a gate requires a valid
verdict, and conflicting envelope/body verdicts are rejected.

Snapshots and analysis are not the only things that can go unobserved: the
run itself can end early. A sandbox envelope therefore folds the outcome of
`execution` into the same `coverage` block, as the area
`installer execution` — stage `timeout` when the job was killed at the
deadline, stage `exit` when the installer reported a code that is not success
(or no code could be read). Those files are still analyzed and reported: the
delta of a partial install is real evidence, it is just not evidence of a
*complete* install, and nothing in the file tree distinguishes the two.
On Windows, `1641` and `3010` are treated as success (installed, reboot
requested), so a reboot-requiring MSI is not reported as a failed run. The
writer and the archive validator share one function for this
(`universal_sandbox::run_issue`), so a saved report cannot claim complete
coverage while its own `execution` block says the installer was killed.

## One verdict, three evidence sets

A sandbox run produces three analysis bodies: `installer_report` (the binary
that was run), `report` (the install tree) and `drops_report` (files added or
modified elsewhere inside the sandbox — the redirected profile, startup
folders, and so on). "Elsewhere" includes the installer's own temp folder
and its working directory: `TEMP`/`TMP` point at `tmp/` and the process runs
with `work/` as its working directory, so those are the installer's folders,
not sandbox bookkeeping. The whole-sandbox delta filters out only what is
actually ours — the `install/` tree (reported separately), the registry hive
file, and the two `work/installer.*.log` capture logs. Filtering `tmp/` and
`work/` wholesale, as an earlier version did, made a payload staged in the
installer's temp invisible: not in the delta, not analyzed, not recorded as
excluded. The envelope's `verdict`/`risk_score` are the **worst**
of the three, and `verdict_sources` records each part's score so the decision
is explainable. Worst rather than sum because the installer is frequently
copied into its own install tree: summing would score one binary twice.

Drops are analyzed natively, not through external REA: REA is invoked per
target, and aiming it at the sandbox root would feed it our own bookkeeping.
Each dropped path is re-checked with `symlink_metadata` immediately before
analysis so a link planted after the snapshot cannot pull an outside file
into the report. A part that could not be analyzed is `null` in
`verdict_sources`, with the reason in `installer_error` — never a silent zero.

Because `verdict_sources` is part of the record, validation can check the
arithmetic: an archive whose envelope is calmer than its worst listed part is
rejected rather than rendered or gated.

## imphash is a shared convention, not a local one

An import hash is only useful if it means the same thing in VirusTotal, YARA
and this tool. The normalization therefore mirrors pefile's `get_imphash()`
exactly: file order, lowercase, extension stripped only for `.ocx`/`.sys`/
`.dll`, ordinals left in position and library-qualified, joined with `,`,
MD5. `imphash_source()` returns the pre-hash string so any digest can be
re-derived by hand.

Ordinal imports are the subtle part. pefile resolves them through
ordinal->name tables, and those tables have been corrected over time — which
silently changed imphash values. Upstream now keeps a second, frozen copy
used only for imphash, documented as preserving compatibility with YARA,
YARA-X and other implementations of the original algorithm. That frozen copy
is what `src/imphash_ordinals.rs` contains, including the quirk that
`wsock32.dll` is looked up in the `ws2_32` table. Using the corrected tables
instead would produce digests that disagree with public corpora on 147
`ws2_32` ordinals alone.

The tables are generated by a script that reads a local pefile checkout and
performs no network access; the generated Rust is checked in, so an
air-gapped build needs neither Python nor pefile. Ten reference fixtures were
hashed by upstream pefile and are asserted in the tests, and `doctor`
re-checks two of them at runtime (`hashes.imphash_selftest`) so a mangled
build is caught before an operator quotes a hash in an investigation.

## Coverage is part of the evidence

A manifest is only useful if it says what it could not see. `Snapshot::capture`
never aborts on a failure — a partial manifest beats none — but every failure
is recorded as a `ScanIssue` with a stable stage: `traverse`, `entry`,
`metadata`, `path`, `hash`. `Snapshot::is_complete()` is therefore a claim the
tool can actually back: when it is true, absence from `entries` means absence
from disk.

The same reasoning applies to the diff. A regular file with an empty digest
was not read, so comparing two empty digests proves nothing. Those entries go
to `Delta::unverified` rather than `unchanged`. Size and kind are compared
first, because a change in either is proof of modification without any hash.
Directories and symlinks legitimately have empty digests and are excluded, or
every snapshot would warn about every folder.

`app::coverage_block` merges snapshot issues, per-report analysis limits and
uncomparable files into one envelope `coverage` block, each entry labelled with
the area it came from ("sandbox snapshot (after)", "drops analysis", …). It
never touches the risk score: coverage describes the evidence, not the sample.
`report::validate_coverage` then checks the block against the issues it lists
and the bodies it summarizes, so an archive cannot be made to look clean by
flipping one boolean. `--fail-on-incomplete` turns the same record into exit
code 3, which lets CI refuse a calm verdict that rests on partial evidence.

The verdict itself is checked the same way. A body's score is fixed
arithmetic over its findings (sum, capped, floored by the worst severity,
banded), and the writer derives it with `rules::risk` every time — so
`report::validate` recomputes it from the serialized findings
(`rules::risk_from_serialized`) and refuses a body whose recorded score,
verdict, finding count or severity counts disagree, a verdict outside its
own score's band, or a scan envelope whose score differs from its body's.
Findings are never re-derived from files at load time; the archive is
judged against its own evidence, which is all a gate ever has. The one
combination the envelope legitimately makes — a sandbox run's
`verdict_sources` — is checked against the bodies the entries were
copied from, and each body's reader-facing `summary` against the body,
so no restatement of a verdict anywhere in the file can be calmer than
the verdict it restates.
